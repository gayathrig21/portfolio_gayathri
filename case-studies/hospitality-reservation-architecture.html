02 / DISTRIBUTED SYSTEMS / SYSTEM DESIGN

Cloud-Native Hospitality Reservation Architecture

An OPERA-aligned system design for read-heavy reservation traffic, transactional booking, reliable event publication, and real-time front-desk updates.

  • Java 21 / Spring Boot 3
  • Kafka / Debezium CDC
  • Redis / CQRS / Saga
The problemArchitectureTrade-offsPublic artifactDesign outcome

01 / THE PROBLEM

Define the operational challenge.

Searching availability and committing a reservation have different consistency and scaling needs. The architecture separates browsing from authoritative booking commands and makes distributed failure recovery explicit.

02 / SYSTEM ARCHITECTURE

Make the flow inspectable.

Reservation, Rate/Inventory, Profile/CRM, Billing/Folio, and Front Desk form the domain decomposition. A GraphQL/REST BFF serves clients. Booking uses inventory coordination and idempotency; outbox events feed Kafka through CDC and update query-side projections.

Sanitized conceptual diagram based on résumé-reported responsibilities and design scope. It is not an internal Oracle architecture document.

03 / KEY ENGINEERING TRADE-OFFS

Explain the choice.

Public discussion of the engineering patterns; internal decision records and implementation details are not reproduced.

Key engineering trade-offs
ApproachAlternativeRationale / trade-off
Transactional Outbox + CDCDatabase/broker dual writesCommit domain state and event intent together; consumers still need replay-safe handling.
Saga compensationA cross-service database transactionCoordinate booking and payment steps while allowing independent services; compensation adds recovery complexity.
CQRS + RedisAll browsing reads hit the booking storeScale the read-heavy path independently; recheck availability at booking time.
GraphQL/REST BFF + event updatesDirect UI fan-out to all servicesCompose client views and real-time updates behind a bounded API layer.

05 / DESIGN OUTCOME

Architecture with explicit constraints.

The outcome is a system design covering domain boundaries, concurrency controls, resilience, integration, and observability. It is presented as architecture work, not as a publicly deployed reservation product.

Design assumptions/targets: 100:1 look-to-book workload and sub-50ms caching. No measured throughput or latency claim is made. The design includes inventory locking, idempotency, Resilience4j, tracing, and payment tokenization boundaries.

Professional context and experience are documented in the résumé. Public examples use generic entities and synthetic data.
